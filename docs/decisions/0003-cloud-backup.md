# ADR 0003：3.0 先交付可恢复的云端备份

日期：2026-10-07
状态：历史方案，已由 [ADR 0004](0004-local-backend-learning.md) 取代。3.0e 移除 App 云端入口和依赖；真实 Supabase 和 Android 云端验收未完成。

## 背景

本地 MVP 将全部数据保存为 AsyncStorage 的 `lingonest.v2` 快照。它适合离线学习，但换手机或卸载应用后不能找回。当前数字 ID 也没有设计跨设备合并所需的全局身份。

## 决策

- 保留本地快照作为日常读写来源；账号是可选功能。
- 使用 Supabase Auth 的邮箱验证码、PostgreSQL 的单用户 JSONB 备份行和逐行访问规则。一次备份保存整个 v2 快照，不改动卡片 ID 或复习规则。
- 备份只在用户确认后发生；数据库以原子版本比较拒绝过期设备的写入。
- 恢复只在用户确认后发生；先保存本机恢复副本，再写入云端快照。无效数据不能覆盖本机。
- 账号会话存于设备安全存储；客户端只包含 Supabase 公共项目 URL 和 publishable key。数据库服务密钥、未来的 AI Key 留在服务端。

## 取舍

JSONB 快照让旧数据无损上传并把 3.0 控制在一个可验收闭环内，但不能高效地查询跨设备的单个卡片，也不提供自动合并。若将来需要双向同步，再把卡片、分组、复习记录拆成独立表，并设计全局 ID、删除记录和冲突策略。当前只宣称“备份与恢复”，不宣称实时同步。

Supabase 比自建 Node 服务少了账号、数据库部署和权限基础设施的工作；Firebase 也可实现，但与未来 PostgreSQL 数据分析和关系建模路线不一致。TanStack Query 暂不引入，因为 3.0 只有一份手动操作的远程备份，无需额外缓存层。

## 安全与验证

`supabase/migrations/202610070001_user_backups.sql` 启用 RLS，只允许认证用户读取自己的行；写入仅通过取 `auth.uid()` 的函数完成。公开的 publishable key 不是服务密钥，不能替代数据库权限。必须使用两个测试账号实测隔离，并验证断网、过期版本、错误快照和本机写入失败。
