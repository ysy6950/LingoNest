# LingoNest 问题与排错记录

本文件记录开发过程中遇到的错误、排查过程、解决方案和可复用的经验。问题不是失败记录，而是理解系统边界和工程方法的重要学习材料。

## 2026-10-29：AI 练习请求返回上游 HTTP 404

- **现象**：电脑后端显示 AI 和词典配置均为 `configured`，但 AI 练习请求在约 1 秒内连续失败，错误为 `provider_not_found` / HTTP 404。`configured` 仅表示本机必需配置项齐全，不代表服务商接受了请求。
- **排查**：本机 `.env` 中的模型标识为 `gpt-6-sol`。在电脑后端使用当前 AI Key 查询服务商模型列表时，服务商返回 HTTP 200，但列表只有 `gpt-image-2`，没有当前配置的文本模型；Key 仅用于向既定服务商认证，未输出到聊天或日志。Base URL 自动拼出的 Chat Completions 路径与服务商公开格式一致。
- **根因确认**：原密钥分组已不再提供 `gpt-6-sol`，因此服务商对练习请求返回 HTTP 404。用户切换到提供该模型的较高倍率分组后，AI 功能恢复。
- **处理与边界**：可用模型由当前 Key 的分组决定，公开模型列表不保证每个分组都能使用。更换分组前应核对可用模型及倍率/费用；修改电脑端 `.env` 后须重启后端。手机端不需要重装或清除数据。
- **复测提醒**：服务商控制台确认模型属于当前 Key 分组后，只发起一次 AI 请求并查看使用记录。不要连续点击；不要把 API Key、`.env` 内容或完整认证请求发到聊天中。

## 2026-10-28：词典请求超时后恢复

- **现象**：手机查询词典资料时显示请求失败，电脑后端日志分类为 `timeout`；稍后重试恢复正常。
- **判断**：这表示后端在规定时间内没有拿到词典服务响应，不等于 Key 一定错误，也不等于单词数据损坏。
- **处理**：确认后端仍在运行、网络可达后再重试；不要连续点击，以免服务商仍在处理前一次请求。成功前不会覆盖原解释、复习记录或已有发音资料。
- **当前边界**：词典后端请求上限 10 秒，手机等待上限 15 秒。真实网络耗时未作为固定性能指标写入项目，只记录错误类别。

## 2026-10-28：缓存和用量的预期行为

以下是 4.5 的设计边界和自动检查覆盖项，不是用户已报告的手机故障。

- **重复生成总是相同内容**：同词同义的分析/推荐可能命中 24 小时缓存，设置查询可看到命中增加。若内容确需重新生成，确认清理电脑缓存后再试；清理保留手机笔记。修改原解释会区分词义，也会生成新请求。完成的练习题不缓存，但模型仍可能碰巧生成相似句子。
- **显示已有两个 AI 任务**：同时处理数量已满。等现有任务结束再手动请求，不会自动排队或重试；缓存命中与同输入合并不增加新任务。此限制不能等同每小时预算或费用上限。
- **查询用量提示接口不存在**：可能仍运行旧后端，或只启用了连接检查。按当前局域网备份模式重启后端、用新码配对并重载 App，不需要重新填写 AI Key。
- **服务重启后计数为零**：缓存和计数只在电脑进程内存，重启归零正常；手机已保存资料与 SQLite 备份不受影响。用量需点击“查询用量”刷新，数值不是实时推送，也不包含词典请求。
- **超时但服务商仍计次**：后端统计一次失败尝试，不自动重试；不能保证服务商没有继续处理或不收费。统计中的“调用”不是实际计费笔数或金额。
- **清缓存时已有请求仍返回**：清理不取消正在进行的生成，但其结果不能回填刚清理的缓存。完成前重复同输入仍共享旧任务；等待结束后再次生成才会新调用。自动测试覆盖这个边界，不能通过连续点击来判断清理失效。
- 验证：后端 44 项、手机 87 项测试、两端类型检查及 Android 导出通过；多宽度页面检查覆盖查询、清理、取消、旧接口提示及连接变化后的迟到响应。手机真实回归见 [4.5 测试计划](../testing/AI_4_5_TEST_PLAN.md)。

## 2026-10-27：练习生成成功但题目必须由程序验收

- **风险**：如果直接采用 AI 返回的选项、答案索引或分数，模型一次格式或语义错误就可能让用户看到错误答案，甚至污染复习数据。
- **处理**：后端只接受 4～5 个已有单词和固定的题目草稿；手机重新校验题目，自己生成四个选项、记录用户选择并判分。AI 返回多余答案字段会被拒绝。
- **歧义边界**：语言模型可能生成多个词都说得通的句子，用户可跳过或排除该题；排除题不计分，不把程序校验误认为语言事实核实。
- **验证**：自动测试覆盖非法字段、重复题、错误空缺、陌生单词、重复点击、源词变化和超时；真实题目质量仍需按 4.4 测试计划人工抽查。

## 2026-10-27：推荐频繁超时，但服务商请求次数增加

- 现象：用户报告部分较复杂、不常见单词频繁失败，后端打印 `[AI] recommendation failed: timeout`；服务商仍增加请求次数。其他测试没有报告问题。
- 定位：该日志来自后端 AI 生成阶段，原截止时间只有 15 秒。手机推荐虽等 35 秒，但无法挽回后端先中止的请求。构词说明增加了输出内容，原上限偏紧；是否词汇难度导致变慢仍需耗时证据。
- 修复：AI 笔记和推荐统一后端 90 秒、手机 120 秒。词典核对仍并行执行，每项最多 10 秒；推荐成功记录 AI/词典/总耗时，失败记录经过时间，不记录密钥、单词正文或供应商原始返回。错误提示说明可能已经处理及勿连续重试。
- 边界：取消等待不能保证服务商撤回已收到的请求，也不能保证退款或不计次；本程序不自动重试，没有后台找回超时结果。延长等待也不能解决所有服务商故障。
- 验证：两端类型检查、手机 74 项和后端 28 项测试通过，新增虚拟计时测试覆盖慢成功、最终超时、清除计时器和无自动重试。更新后须重启原局域网后端、用新配对码连接并重载 App；不改 `.env` 或清除单词。真实服务商及手机回归待用户确认。

## 2026-10-27：构词说明的更新与校验边界

以下为本轮设计和自动检查覆盖的边界，不是用户已报告的手机故障。

- **能生成但提示构词说明暂缺**：可能电脑仍运行旧后端。重启原局域网服务，用新配对码连接，再重载手机和重新生成；无需改 `.env` 或清空单词数据。
- **显示构词待确认**：不是网络故障，表示构词细节无法可靠说明；不应改成猜测的词根。“词典查到词形”也不能把这条关系升级成已核实词源。
- **构词说明格式无效**：模型可能漏字段、给错类型、为不确定分类填入猜测，或返回额外认证字段。两端会拒绝非法结构；可重新生成并记录错误类别，不应先改 IP 或泄露服务商原始返回。
- **预览中有词根，加入后的卡片没有**：当前构词分析只在推荐页临时展示；确认只加入普通单词卡，不保存关系分析。不需要为此升级或重建 v3 数据。

## 2026-10-27：自动补全的预期状态与排查入口

以下是本轮设计和自动检查覆盖的边界，不代表用户已经在 Android 上遇到这些故障。

- **新词已保存但资料没出现**：到设置查看“补全待办”。“等待连接电脑”表示未配对；确认后端运行并在设置连接电脑即可，不需要重加单词。词典和 AI 分别显示失败，可只重试失败项。
- **重开 App 后没有继续**：待办在手机保留，配对码没有落盘；重新配对，并保持 App 在前台。电脑 IP 改变或后端重启换码时同样需重连。
- **开关开启，旧词没有自动补齐**：这是范围控制。开关只作用于此后新词；旧词在详情页选“补全缺失资料”，恢复备份也不会整库自动补全。开始恢复会取消旧待办，恢复失败后需要的任务也应重新选择。
- **有音标但没有美式音频或词性**：词典不保证每个词都有全部资料。成功查询会保留可用字段并结束该任务，不无限重复调用；需要时可手动再次查询，不能伪造词典音频。
- **保存失败**：核心单词或待办保存出错时暂停请求，先使用对应的“重试”保存成功再继续。手动取消、改词、删除或编辑资料后，迟到的自动返回会被忽略。

## 2026-10-26：关联词的换行解释与词典核对边界

- 开发时发现的输入边界（不是用户报告的线上故障）：推荐加入的默认解释是“英语解释 + 换行 + 中文提示”，原 AI 输入校验只接受单行。若不处理，再对新词生成 AI 内容会因格式被拒绝。
- 处理：后端只对发给 AI 的解释把换行转换成空格，仍保留 500 字符限制；手机保存的原解释不改。自动测试验证提示词携带正常化后的当前词义。
- 另一条核对边界：词典的建议列表和不相关词条不能算候选匹配。新增测试区分词条 ID、词头、词形命中与单纯拼写建议；词典失败时返回“尚未核对”，不是“已查到”。词形存在仍不能证明语义关系正确，真实推荐质量须人工检查。
- 验证：两端自动检查通过；真实服务商与 Android 4.3 验收待完成。更新后端代码后应重启旧进程并更新手机配对码，避免把旧进程的 404 误判为网络故障。

## 2026-10-26：美式发音无声与连接信息反复输入

- 现象：查得到音标，美式音频按钮点击后不出声；AI、词典和备份每次换页都要求输入电脑地址和配对码。
- 原因：音标查询与音频播放是两条不同的请求。后端拼接媒体 URL 时漏掉词典规定的文件子目录；播放器没有读取加载错误。连接字段分别放在各页面组件内，离开时清除。
- 修复：后端按音频文件名前缀生成目录；手机读取旧卡片或旧备份时修复旧 URL，保留单词与复习记录。播放器显示加载、失败和超时。共享连接成功后跨功能复用，仅电脑地址保存在手机；配对码只留在 App 运行内存，重开 App 或服务重启后重新配对。
- 验证边界：自动测试和公开示例音频 HTTP `200 audio/mpeg` 已确认；具体手机声音、手机网络与当前单词的供应商音频文件仍需 Android 实机确认。

## 2026-10-23：电脑能连接，AI 预览却提示暂不可用

- 现象：Android 已输入可用于连接电脑的 IP、端口和配对码，但“生成预览”提示 AI 服务暂不可用；旧后端没有可用的失败分类日志。
- 排查：本机配置填写的是服务商 Base URL（以 `/v1` 结尾），旧代码却把该地址直接当作 Chat Completions 完整接口调用。健康检查和备份属于电脑后端，不能证明后端到 AI 服务商的请求成功。
- 修复：后端将 Base URL 补成 `/v1/chat/completions`，也兼容已填完整接口的配置；按服务商 HTTP 状态区分鉴权、路径、请求格式和限流失败。手机显示对应的安全提示，电脑只记录错误类别和上游 HTTP 状态，不记录 Key、请求或响应正文。
- 验证边界：模拟服务商的自动测试已通过；真实服务商和 Android 重试仍待用户验收。使用 `npm.cmd start` 时，代码修改后必须停掉旧进程再启动，新的配对码也要重新填写。

## 2026-10-17：移除旧云端包时 npm 报 ERR_INVALID_URL

- 现象：`npm.cmd uninstall` 在解析依赖时出现 `ERR_INVALID_URL`，堆栈指向 npm 代理 URL 处理；它未修改 `package.json` 或锁文件。
- 处理：只用补丁删除三个直接依赖，再运行 `npm.cmd install --package-lock-only --offline --legacy-peer-deps` 更新锁文件；没有运行强制版本升级或清理手机数据。之后必须重跑类型检查、测试和 Android 打包。
- 经验：包管理命令失败后先检查工作树和锁文件，不要假设依赖已成功删除；网络代理问题不应通过降低 App 安全设置来绕开。

## 2026-10-17：TypeScript 检查通过，但 Node 测试报不支持语法

- 现象：新增请求模块在 `tsc --noEmit` 通过后，`npm.cmd test` 报 `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX`。
- 原因：手机测试使用 Node 的 `--experimental-strip-types`，它会擦掉类型，却不转换所有 TypeScript 特有语法；`constructor(public code: string, ...)` 同时隐式创建字段，无法只擦掉类型。
- 修复：把字段声明为 `code: string`，构造函数中明确执行 `this.code = code`。未引入新的编译工具或依赖。
- 经验：类型检查回答“类型是否一致”，不保证执行环境支持所有语法。要在项目实际使用的测试命令中验证。

## 2026-10-17：备份请求失败不一定代表电脑没有保存

- 这是自动化模拟的边界情况，不是已报告的 Android 故障：电脑可能已把请求写进 SQLite，成功响应返回前网络断开。
- 处理：App 明确提示可能已保存，要求重新读取；不自动重试覆盖。版本检查可以拒绝重复的旧版本写入。
- 另一个被测试的边界：恢复过程的留档、指针或正式快照任一步写入失败，当前手机数据仍保留，重启后可读取；不能通过卸载清数据来“修复”。

## 2026-10-17：连接检查成功但读取不到电脑备份

- 现象：手机能访问电脑，但“读取电脑备份”失败；电脑启动输出曾显示 LAN backup。
- 排查：直接访问电脑的 `/health`，发现返回 `mode: lan-health-only`；此模式只提供连接检查，`/backup` 会返回 404。原因是旧的 3.0c 服务仍占用 3001，新备份服务没有成为当前监听者；配对码属于每次启动的临时凭证，旧码也不能用于另一个进程。
- 处理：在运行旧服务的终端按 `Ctrl+C`，确认 `GET /health` 返回 `mode: lan-backup` 后，再使用同一次启动输出的配对码。现在端口被占用时服务会打印明确提示。
- 经验：先看服务实际返回的模式，再判断手机页面；“能连上电脑”只证明健康检查可达，不代表备份路由已启用。

## 2026-10-03：AsyncStorage 原生模块为空

### 现象

加入本地持久化后，Expo Go 报错：

```text
AsyncStorageError: Native module is null, cannot access legacy storage
```

### 当时的假设

最初怀疑是从 `react-native` 核心包导入了已经移除的旧版 AsyncStorage。

### 排查动作

1. 检查 `App.tsx` 的导入路径。
2. 确认实际安装的依赖版本：

```text
@react-native-async-storage/async-storage@3.1.1
```

3. 运行 `npx expo install --check`，发现 Expo SDK 57 推荐版本是 `2.2.0`。

### 根本原因

导入路径本身正确，但 AsyncStorage `3.1.1` 与当前 Expo SDK 57 的原生模块版本不兼容，导致 JavaScript 接口存在而原生模块为空。

### 解决方案

使用 Expo 的兼容安装命令：

```powershell
npx expo install @react-native-async-storage/async-storage
```

并用 `npx expo start -c` 清理 Metro 缓存后重新加载 Expo Go。

最终版本：`@react-native-async-storage/async-storage@2.2.0`。

### 以后如何更快判断

- Expo 项目安装原生依赖时优先使用 `npx expo install`，不要直接使用普通 `npm install` 追最新版。
- 遇到 Native module 错误时，同时检查导入路径、依赖版本、Expo SDK 兼容性和 Metro 缓存。
- 不要直接运行 `npm audit fix --force` 解决版本问题，它可能引入不兼容的重大升级。

## 2026-10-05：单词组顶部按钮被遮挡

### 现象

单词组功能加入后，默认组按钮在手机顶部只露出一部分，用户无法确认它是什么。

### 根本原因

主容器仍使用 `justifyContent: 'center'`。当页面内容高度超过手机屏幕时，整个内容块被居中，顶部内容可能超出可视区域。

### 解决方案

- 主容器改为从顶部开始布局，并使用安全区域和单一外层纵向 `ScrollView`。
- 将内容较长的页面交给外层滚动容器，避免多个区域争抢剩余高度。
- 重新按“单词组 → 当前组 → 添加单词 → 单词卡”的顺序排版。

### 经验

移动端页面内容变长后，不能只验证短内容状态；需要验证小屏幕、滚动和顶部安全区域。

## 2026-10-06：默认组有数量但单词卡不可见

### 现象

页面显示默认组有单词数量，但用户看不到对应的单词卡；同时原来的“新建单词组”和“添加单词”放在同一块区域，操作层级不清楚。

### 根本原因

原页面在内容变长后仍依赖复杂的布局分配，卡片区域没有稳定地成为可滚动内容的一部分。默认组数量和卡片列表虽然使用了同一份数据，但视觉上被顶部布局和滚动区域遮挡，造成“有数量、看不到卡片”的体验。

### 解决方案

- 使用一个外层纵向 `ScrollView` 承载整个页面，确保默认组、添加表单和卡片列表按顺序可滚动查看。
- 将单词组创建改为列表最前方的“＋”按钮和弹窗，和添加单词表单分离。
- 首次本地运行时补充 4 张演示单词卡，并通过单独的本地标记避免每次重启重复添加。
- 在卡片中提供明确的“单词/解释”面、翻面提示、修改、删除、复习和移动入口。

### 以后如何更快判断

- 同时检查“数据计数”和“数据列表”是否使用同一筛选条件。
- 移动端长页面优先验证：首屏、滚动到底部、空列表和多卡片状态。
- 功能入口应按用户任务分组，创建分组不应和添加单词混在同一表单中。

## 2026-10-05：单词移动和移出设计

### 产品决策

第一版继续让每个单词只属于一个组。移动单词就是修改它的 `groupId`；移出单词不是删除，而是移动到系统组“未分组”。

### 原因

这样能满足“移出”和“加入另一组”，又不需要立即引入多对多关系、关联表或复杂选择器。以后如果一个单词需要同时属于多个组，再单独升级数据模型。

## 2026-10-24：词典显示 configured，但查询失败

### 现象与原因

后端已读取 `LINGONEST_WEBSTER_KEY`，真实 `learn` 请求也到达供应商；但供应商返回 HTTP 200 的纯文本“无效 Key”，并非正常词典 JSON。原处理会把它报成笼统的供应商失败。`configured` 只检查本机配置齐全，不能证明上游授权。

### 处理与结果

后端现在把这一特殊响应归类为 `provider_auth`，日志和手机都不显示原始响应或 Key。用户随后在词典后台修正 Key，并报告成功取得音标。遇到同类问题时，确认 Key 属于 Learner's Dictionary 且已启用，修改 `.env` 后重启服务；不要把 Key 粘贴到聊天中。

## 2026-10-26：词典音标成功后如何播放两种口音

### 判断

词典查询成功只说明后端拿到了结构化词典结果，不代表每个单词都一定有音频。Merriam-Webster 返回的 `sound.audio` 文件名存在时，后端才生成固定美式媒体地址；文件名不符合安全格式时丢弃音频字段，避免把供应商返回内容直接当作 URL。

### 处理与结果

手机端加入 Expo Audio 播放美式词典音频，另用 Expo Speech 的 `en-GB` 播放英式设备朗读。音频字段加入 v3 快照校验，不影响已有只含 IPA 的旧卡片。自动测试覆盖安全 URL、旧快照保存和两端请求校验；Android 实机播放仍需按 4.2 清单确认。

## 2026-10-26：Expo Go 与项目 SDK 不兼容

手机 Expo Go 已是 SDK 58，项目仍是 SDK 57，因此 Expo Go 在加载代码前拒绝打开。按 Expo 官方升级流程将 `mobile/` 的 Expo、React Native、React、Router 和原生模块更新到 SDK 58 匹配版本；未卸载手机 Expo Go，也未改动本地单词快照格式。

安装时 npm 全局代理地址缺少 `http://`，因此首次命令报 `ERR_INVALID_URL`；本轮安装命令临时传入完整代理地址。旧版 Router 的可选依赖造成 npm 解析冲突，曾用 `--legacy-peer-deps` 过渡安装；依赖树更新后普通 npm 安装、锁文件干运行和 Expo Doctor 均通过，未持久化忽略依赖检查的配置。最终移动端 41 项测试、类型检查、Android/Web 导出及发音页网页回归通过；手机启动和旧数据仍需实机确认。不要为排查版本问题卸载 Expo Go 或清除应用数据。
